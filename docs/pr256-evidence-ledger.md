# PR #256 evidence ledger

**Scope:** [`uunicorn/python-validity#256`](https://github.com/uunicorn/python-validity/pull/256), from its opening on 2026-05-19 through the last audited public comment on 2026-08-10.
**Evidence policy:** primary sources only: the PR body, PR comments/review, commits on the PR branch, and repository source. Tester statements are recorded as reports, not silently promoted to independently reproduced facts.  
**Privacy:** this ledger intentionally omits fingerprint frames, template payloads, TLS private material, host serials, and long raw protocol blobs that appeared in diagnostic logs.

## Executive finding

PR #256 has strong evidence for **normal operation on already-provisioned sensors** across both USB IDs and both observed real sensor types. It has an artifact-backed zero-partition result for **`138a:00ab` / `0xd51`** at commit `62ee97f`, plus an independent successful factory-empty report for **`06cb:00b7` / `0xd51` / `FM-3439-001`** using the identical HP DLL payload. The latter still needs a pinned patch and before/after artifacts. The exact factory-reset sequence for `06cb:00b7` / `0x969` remains unknown. USB VID:PID alone cannot select behavior: both `138a:00ab` and `06cb:00b7` have been observed reporting more than one real sensor type.

## Validated facts

1. **VID:PID does not determine the real sensor type.** `138a:00ab` has reported both `0xd51` and `0x969`; `06cb:00b7` has also reported both. Runtime sensor identity must drive protocol behavior. [mpsijm `138a:00ab/0x969`](https://github.com/uunicorn/python-validity/pull/256#issuecomment-4532902308) · [pianist `138a:00ab/0xd51`](https://github.com/uunicorn/python-validity/pull/256#issuecomment-5168647804) · [Karloss1234 `06cb:00b7/0x969`](https://github.com/uunicorn/python-validity/pull/256#issuecomment-4613857979) · [RamcharanRajpurohit `06cb:00b7/0xd51`](https://github.com/uunicorn/python-validity/pull/256#issuecomment-4753840622)
2. **Both `0xd51` and `0x969` need the direct `b[0] == 3` capture path.** Multiple hardware reports show enrollment/verify hangs before the gate and progress after it; the implementation is sensor-type-scoped. [PR body / `0xd51`](https://github.com/uunicorn/python-validity/pull/256) · [Karloss1234 / `0x969`](https://github.com/uunicorn/python-validity/pull/256#issuecomment-4613857979) · [`0c00f0a`](https://github.com/uunicorn/python-validity/commit/0c00f0a6d5ae9070c9da46b40af1296bf0b4f97c)
3. **Mutating the shared hardware-table identity broke later opens, and volatile calibration broke reboot durability.** These failure mechanisms are supported by both the tester's source-level diagnosis and the corresponding fixes. [report](https://github.com/uunicorn/python-validity/pull/256#issuecomment-4950596487) · [identity-copy fix](https://github.com/uunicorn/python-validity/commit/fddbd07011d3759a0282fa20cc95af1d80095e65) · [persistent-calibration fix](https://github.com/uunicorn/python-validity/commit/01500cbdc5a0c60a0f2484e8afcd7ba3bc7d6f21)
4. **Zero-partition `138a:00ab/0xd51` provisioning works for the captured ROM/sensor identity at `62ee97f`.** The proof includes a before probe, creation of five partitions, firmware transition, enrollment, verification, and attached logs. [implementation](https://github.com/uunicorn/python-validity/commit/62ee97f18b66890df78ce8de1f0a745d144fd53f) · [hardware result](https://github.com/uunicorn/python-validity/pull/256#issuecomment-5209862230)
5. **The then-current Debian install path could touch the biometric device without an explicit first-run action.** `dh_installsystemd --no-start` was insufficient because the post-install udev trigger activated the service through `SYSTEMD_WANTS`. [chrisos86 observation](https://github.com/uunicorn/python-validity/pull/256#issuecomment-5228268569) · [PR-head packaging context](https://github.com/uunicorn/python-validity/commit/c809f5d23b23a7628433fed0d1fe41c3dea96f0f)
6. **An interrupted fwext upload leaves partition 2 non-bootable until it is erased.** gfiguero observed `get_fw_info(2)` repeatedly return `044f` after a service restart during upload, then restored the reader by erasing only partition 2 and uploading again. The error path is present in the current PR source. [hardware report](https://github.com/uunicorn/python-validity/pull/256#issuecomment-5237758333) · [current upload path](https://github.com/uunicorn/python-validity/blob/62ee97f18b66890df78ce8de1f0a745d144fd53f/validitysensor/upload_fwext.py)

## Unresolved gaps and required next evidence

1. **Zero-partition `06cb:00b7` has one successful `0xd51` report but is not release-proven across the family.** Repeat the pianist protocol on the exact `FM-3439-001/0xd51` identity with a pinned revision, before/after probes, enrollment, correct/wrong verification, reboot, and resume; separately repeat it for `0x969`. The current `0x969` report is useful but not reproducible enough. [d51 report](https://github.com/uunicorn/python-validity/pull/256#issuecomment-5237758333) · [969 report](https://github.com/uunicorn/python-validity/pull/256#issuecomment-5190421894)
2. **Factory reset remains device-specific and incomplete.** `06cb:00b7/0x969` accepts related blobs but rejects a later reset command; `138a:00ab` legacy reset paths returned `0404`; `06cb:00cb` has its own verified blob. Reset, clean-slate bootstrap, database erase, and host re-pairing must remain separate operations with separate safety gates. [Karloss1234 reset investigation](https://github.com/uunicorn/python-validity/pull/256#issuecomment-5190421894) · [ggiesen device-specific reset](https://github.com/uunicorn/python-validity/commit/bfaeb4e37616118d52f62bd41cbe887a5ef74cb0)
3. **Durability after the August lifecycle fixes needs a defined soak test.** The July reliability failure predates `fddbd07`, `01500cb`, and the operation/session fixes, but the thread lacks a multi-day, multi-reboot, suspend/resume, cancellation, delayed-touch result with version-pinned logs for every device family. [pre-fix failure](https://github.com/uunicorn/python-validity/pull/256#issuecomment-4950596487) · [lifecycle series](https://github.com/uunicorn/python-validity/commit/d1a67b3e66d2f2eb78dc989d7701c3e3c930a8bb)
4. **Negative matching and database lifecycle coverage is uneven.** Several reports prove correct matches, but few prove wrong-finger rejection, no-template interrupt handling, re-enrollment replacement, deletion, nearly-full DB behavior, and Windows/Linux coexistence on the same exact revision. [no-template report](https://github.com/uunicorn/python-validity/pull/256#issuecomment-5142237515) · [DB findings](https://github.com/uunicorn/python-validity/pull/256#issuecomment-4924985981)
5. **Installation behavior and distribution coverage remain incomplete.** The tested PR head contacted hardware during `dpkg` through a global udev trigger. Local hp17 work removes mid-transaction sensor contact and PAM mutation, then defers activation to the next real matched-device add event; that policy still needs upgrade/reboot testing. Fedora/Arch packaging and open-fprintd dependency guidance also need maintained, version-pinned paths. ## Release-evidence bar

A durable upstream claim should be made per **runtime real sensor type + hardware identity + flash state**, not only per VID:PID. For each supported row, retain sanitized evidence for:

1. cold boot and daemon registration;
2. enrollment with real capture stages;
3. correct match, wrong finger, and no-template behavior;
4. cancellation, delayed touch, repeated verification, suspend/resume, and reboot;
5. provisioned and zero-partition paths separately, with destructive provisioning enabled only for an exact validated identity.
